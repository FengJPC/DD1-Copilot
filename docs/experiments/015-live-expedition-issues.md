- 秘密房入口可识别；万能钥匙开启远古神器后成功获得谜一般的多方晶体、巴利斯坦的头颅和朱妮娅的头颅。

- 未侦察陷阱被踩中时，结构化事件正确记录 `outcome=triggered`；本次 Dismas 闪避，生命和压力变化均为 0。

## 待处理问题

### P0：实机测试驱动层把最长等待窗口变成了固定八秒延迟

现象：长连接返回体中的 `elapsedMs` 显示，状态读取通常为 15–239 ms，战斗动作通常为 0.3–0.7 秒；但测试时终端调用的墙钟时间稳定约 8.0 秒。短等待复测时，同一状态查询为 127 ms，中间层到调用方的总墙钟时间约 0.26 秒。

原因：测试驱动层每次写入长连接后使用 8 秒等待窗口；由于辅助进程是常驻进程，终端工具不会按单行响应自动结束，而是等满窗口才交还输出。内存监听与状态归约本身并没有数秒延迟。

处理：后续以约 250 ms 的短等待读取首个响应；若动作仍在运行，再轮询同一终端会话。辅助进程继续逐行输出 JSON，不增加固定睡眠。README 已补充调用约束。

### P0：战斗语义结果出现后，旧行动者仍可能短暂可操作

现象：技能在伤害、治疗或增益日志出现后即可在 0.3–0.7 秒内确认成功，但游戏动画与回合交接尚未完成；紧接着读取时可能仍看到相同的行动者、`turnTick` 和技能列表。

影响：若上层立即依据该快照下令，可能重复选择技能，或把正常动画时间误判为内存读取延迟。

处理：Copilot 现在会记录成功战斗动作对应的行动者与 `turnTick`。二者尚未变化时只返回 `combat_resolving`，不给出新动作；回合切换、战斗结束或进入其他阶段后自动解除。新增回归测试覆盖“已有伤害结果但回合尚未推进”的窗口。

### P0：奇物专用补给可被普通背包动作误耗

现象：石棺事件尚未打开时，普通 `use_inventory_item` 曾消耗一把万能钥匙，但石棺仍保持活动状态。

处理：万能钥匙、铁铲和药草现在不能通过普通背包动作使用，只能在游戏明确列出兼容物品的事件选项中通过 `use_item_on_event` 使用。铁处女和传家宝箱已验证正确事件顺序；新增回归测试确保普通动作不会发送任何消耗输入。

### P1：行动栏包含当前站位无法使用的技能

现象：修女站在三号位时，状态仍提供只能从一、二号位使用的锤击，实际选择后进入超时或恢复流程。

处理：Copilot 解析技能详情中的中英文可用站位，按当前行动者位置过滤技能列表；即使调用方绕过列表直接提交，也会在发送输入前拒绝。新增修女三号位的回归测试。

### P0：扎营餐后没有进入可决策的营地技能状态

状态：已修复，待实机复核。

现象：选择 4 份食物的“全饱”后，动作返回成功并记录用餐阶段推进；下一次状态却是 `phase=post_combat`、`context=actions`、`decision=observe`，同时 `camp.phase` 仍为 3、食物快照仍为 10。预期应进入 `camp.phase=6`，列出 12 点休整点、营地技能和合法目标。

影响：模型无法继续选择减压、侦察或防夜袭技能，也无法可靠结束扎营。

建议：用餐成功后主动等待 `camp: phase 3 -> 6` 或新 `inspect_state` 的 `camp.phase=6`；不得只用界面关闭或上下文变化判定完成。若短时间内仍处于过渡状态，返回 `uncertain` 并自动执行一次只读对账。

后续发现：`finish_camp` 实际已让游戏回到 `camp phase=0`，但状态归约器没有把顶层 `phase` 从 `camp` 恢复为 `room`，从而把扎营后普通战斗技能错误投影为营地技能。已在本轮加入最小归约修复，仍需新长连接实机复核。

### P0：单体营地技能目标上下文未被监听

状态：已修复，待实机复核。根因是 Copilot 的技能元素点击绕过了 `campUseSkill`；IPC 现会在营地技能阶段把对应元素点击路由到营地状态机，使 `camptarget` 正常建立。

现象：全队技能可直接结算；单体“巍然屹立”和“鼓舞”点击后，游戏实际已经等待选择英雄，但 DLL 没有发出 `camptarget`，中间层在 12 秒后返回 `uncertain`。随后在画面上选择莫干斯或 Dismas，技能才结算并消耗休整点。

影响：自动目标导航不会运行，单体技能只能靠画面诊断完成；若把超时误当失败并重发，可能取消或错用技能。

建议：监听营地单体技能武装状态或英雄可选箭头，输出明确 `camptarget`；在该上下文中列出四名英雄及稳定索引。完成目标后以休整点下降和压力/状态变化共同核对。

### P0：奇物使用后的状态缓存会阻塞后续移动

状态：已修复，待实机复核。事件选项和事件物品成功后会立即执行一次只读 `inspect_state`。

现象：光明祭坛已消耗圣水并施加增益后，紧凑状态仍显示祭坛活动、圣水数量为 2，导致 `advance_corridor` 以“先处理活动物件”拒绝。额外发送一次只读 `inspect_state` 后才更新为圣水 1、物件已清除。空木箱也出现同类残留。

影响：语义动作实际成功，但 Copilot 仍按旧快照阻塞路线；如果上层误判，还可能重复交互。

建议：所有事件物品和普通奇物结算后立即请求一次 `inspect_state`，并以物品数量、活动物件消失或明确结果事件共同结算。

### P0：秘密房退出路径表达错误

状态：已修复，待实机复核。

现象：进入 `secA` 正常，但 Copilot 曾把退出目标表达为走廊 `coAB`，并尝试用 `W` 退出，实际无效。实机可用路径是打开地图、回到秘密房节点、选中秘密门所在走廊格，再选择端点房间 `rooA` 或 `rooB` 并确认。离开后，秘密门格附近还会错误再次提供 `enter_room`。

影响：可能卡在秘密房，或在离开后重复进入。

建议：秘密房的 `travel_to_room` 只暴露走廊两端的真实房间，不把 corridor area 当作目的地；离开路径按“秘密房节点 -> 门格 -> 端点房间 -> Enter”执行。只有当前导航来源不是秘密房时，秘密门格才提供 `enter_room`。

### P1：远征前补给选择过慢，单次购买可能因状态间隙失败

现象：在补给界面切换物品种类时，中间层从 Home 开始逐项发送方向键，并为每一步等待结算。跨多格选择时观感明显变慢。绷带购买约 0.57 秒；药草购买曾在状态间隙超时，最终未购买，也未自动重试。

影响：远征前准备拖沓；动作失败如果没有完整背包和钱包对账，可能让实际补给与计划不一致。

处理：实测绷带购买动作本身约 0.57 秒，主要观感延迟同样来自测试驱动层固定八秒等待，并非逐格导航本身。调用层改成短等待后暂不冒险批量发送方向键。购买流程新增只读对账：若交易事件落在状态间隙，立即 `inspect_state` 核对目标补给的背包数量；确认已买到则继续，确认未增加则停止且不自动重按。全部购买完成后再次核对目标数量、背包总数和可用的钱包数据。新增“药草交易事件缺失但检查确认到账”的回归测试。

### P1：火把缺少策略阈值提醒

状态：已修复。紧凑状态低于 50 时返回 `low_light`，低于 25 时返回 `critical_light`，并附带火把数量。

现象：从 70 亮度继续探索后，长走廊中下降到 16，直到用户指出画面过暗才补火把。三支火把将亮度恢复到高亮区；随后长距离探索又降到 43。底层读数和 `use_torch` 均正确，缺少的是中间层提示和决策层守卫。

影响：增加受伏击、压力和战斗风险，也让录屏画面过暗，并使 Reynauld 的“光明战士”无法生效。

建议：在进入未知房间、已知战斗前和亮度跌破 50 时，把光照提升为当前决策中的显著提醒；默认目标为 75 以上，扎营前则考虑营火会恢复亮度，避免浪费火把。最终策略仍由模型决定。

### P1：未侦察陷阱不能在踩中前暴露

状态：已按可观测边界修复。侦察到且仍活动的陷阱会提示拆除；未侦察陷阱只能在游戏触发后报告结果，不再把已结算事件描述为可拆除。

现象：`coCD` 的陷阱在地图上仍为未知内容。连续移动到该格后才记录 `trap_started`，由 Dismas 闪避并结算为 0 损失。动作摘要先报告“在陷阱处停下”，容易让上层误以为仍可主动拆除。

影响：上层可能在陷阱已经结算后提出拆除计划；用户看到的说明与实际时序不一致。

建议：区分 `trap_ahead`、`trap_started` 和 `trap_result`。只有侦察到且尚未触发的陷阱才提供拆除；已触发后直接报告结果并继续。

### P1：到达新房间后的状态可能仅有地图结果

状态：已修复，待实机复核。非战斗进房成功后会强制刷新房间、物件、背包和光照。

现象：进入房间后，`enter_room` 可以确认 area 改变，但房间敌人、物件和可选出口有时仍依赖后续显式状态查询。此前还出现过导航缓存丢失后把当前决策房间错误回退为 `rooA` 的情况。

影响：模型可能依据尚未刷新的房间内容做路线选择。

建议：每次 `enter_room` 成功后自动执行一次 `inspect_state`；直到房间内容与当前房间 ID 都刷新后才返回最终成功。

### P2：紧凑状态仍会重复完整地图

状态：已修复。长连接摘要查询会记住上一次 revision，首次为完整基线，后续默认发送 delta。

现象：若使用普通 `state project=summary`，完整 28 区地图仍会重复输出，单次约五千 tokens；只有显式 `mode=delta` 时输出足够小。

影响：实机长流程产生不必要的 token 消耗，也让关键状态埋在地图数据中。

建议：长连接默认以上一次已发送 revision 作为游标；首次发送地图基线，随后只发当前位置、首次访问房间、侦察新增内容和拓扑变化。除诊断外不重复完整地图。

### P2：实机长连接缺少通用只读强制刷新操作

状态：已修复。MCP 提供 `refresh_state`，长连接提供 `refresh`，均可选择同时刷新地图。

现象：遇到陈旧快照时，当前长连接协议没有直接暴露 `inspect_state`。本次只能借助独立 `scripts/inspect-once.mjs` 发送只读命令；沙箱内首次连接命名管道还因 `EPERM` 失败，需要提升权限。

影响：上层对账路径绕远，也让工具权限和活动会话分离。

建议：为长连接增加 `refresh` 或 `inspect` 操作，由同一进程执行只读 `inspect_state`/`inspect_map` 并返回投影后的新 revision。

### P2：摘要阶段命名和残留字段会误导

状态：已修复主要残留字段。战后摘要不再附带陈旧行动者、技能、选中技能和目标；扎营阶段仍以结构化 `camp.phase` 为核对依据。

现象：扎营餐后暂态被投影为 `post_combat/actions`，并混入陈旧 `combat.actor` 与无敌人的战斗字段；房间对象也可能保留旧 `propCount`，但 `props=[]`。

影响：模型难以区分真实阶段、过渡帧和缓存残留。

建议：投影层对 `camp.phase > 0` 给予更高阶段优先级；摘要只保留与当前阶段一致的字段，并在矛盾时标为 `reconciling`。
