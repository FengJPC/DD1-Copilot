# 战斗战术包与 token 去重

日期：2026-09-25

## 目标

战斗决策不能只剩技能名称；模型需要技能效果、站位、生命、压力、异常状态、属性和抗性。优化目标是删除重复传输，而不是删除战术知识。

## 输出分层

每个决策帧始终包含：

- 当前行动者；
- 双方单位的站位、生命、压力和状态；
- 当前行动者的可用技能编号和名称；
- 当前选中技能与目标；
- 光照。

增量更新包含：

- `skillUpdates`：每名英雄首次行动、技能等级或说明变化时发送完整技能文本；
- `profileUpdates`：单位首次出现或属性/抗性变化时发送；
- 英雄的完整特质与疾病列表也属于 `profileUpdates`，首次出现或档案变化时发送；
- `recentResults` / `recentBuffs`：按事件身份只发送新增记录；
- `questUpdate`：任务状态首次出现或变化时发送。

敌方阵容完全替换时自动开始新基线。模型上下文丢失或手动接管后可显式设置 `resetBaseline=true`。

## 实测

以 2026-09-25 最后一场真实战斗的日志归约状态测试：

- 首次完整战术基线：约 1,335 tokens；
- 同一状态的后续决策帧：约 251 tokens；
- 请求 JSON 的伪终端回显已关闭，不再重复进入上下文。

测试帧包含四名英雄、三名敌方/尸骸、五个技能和光照；首次基线还包含技能详情、全体属性/抗性、最近四条结果、最近四条增益和任务状态。

## 验证

- 25/25 TypeScript 自动化测试通过；
- `npm run typecheck` 通过；
- `npm run build` 通过；
- 连续回合测试确认动态生命变化仍会出现，静态资料与旧历史不重复；
- 敌方阵容完全替换测试确认会重新建立基线。

## 英雄档案扩展

游戏侧 `inspect_state` 已扩展为直接枚举远征队员的特质与疾病，并分别输出 `quirks` 和 `diseases`。这些字段不依赖从属性修正反推名称。中间层把它们纳入英雄档案签名，因此普通战斗回合不会重复发送；新增、移除或替换特质/疾病时会产生新的 `profileUpdates`。
