# 第二轮远征：房间进入、陷阱停步与紧凑地图

日期：2026-09-26

## 实机现象

- 队伍在走廊末端按 `W` 后，地图位置已经切换为 `rooF`，但还没有向右走到房间触发点；旧 `enter_room` 已提前报告成功。
- 侦察到的陷阱前，DLL 在约 1.4 秒内输出 `parked short of the trap boundary`，中间层没有把它识别为完成证据，因而继续等到超时。
- DLL 的 `trap_chance` 实机值为 `0.9`，旧测试样本为 `90.0`，上层曾显示为 `0.9%`。
- 调用方显式请求 `mode=compact` 时，摘要仍会重复完整地图。
- 常驻辅助进程的终端读取窗口曾被误当成动作耗时；战斗交接等待也需要明确为上限，而非固定延迟。

## 修复

1. `enter_room` 成为完整事务：过门后发送 `Shift+D`，等待休息点、房间观察、战斗或事件证据，再刷新房间、背包和光照。到达事务意外中断时，状态恢复路径采用相同的向右补完逻辑。
2. 走廊移动把 `released ... parked short of the trap boundary` 作为终态，随后立即执行 `inspect_state`，向模型暴露陷阱与各英雄拆除概率。
3. 解析 `trap_chance` 时，`0..1` 乘以 100，已经是百分数的值保持不变。
4. 长连接记录地图基线是否已经发送。首次摘要提供完整地图，后续摘要仅提供当前位置、逻辑房间、位置 tick 和已访问区域；显式 `includeMap=true` 可重新取得完整地图。
5. 战斗决策等待默认上限为 30 秒，状态一旦就绪立即返回。终端侧读取继续采用约一秒的短轮询，不等待常驻进程退出。

## 验证

- 新增“陷阱前停稳并刷新选择”和“过门后向右走入房间”回归测试。
- 新增比例陷阱概率归一化测试。
- `npm test`：71/71 通过。
- `npm run typecheck`：通过。
- `npm run build`：通过。
- 本轮没有修改游戏侧 C++，不需要关闭游戏或重新部署 DLL。

## 待实机复核

- 当前 `rooF` 门内状态应在新版长连接首次查询时自动补完向右移动，并产生新房间观察或战斗状态。
- 连续探索再次遇到侦察陷阱时，动作应在停稳并刷新后立即返回，不再出现约 14 秒空等。
- 连续两次紧凑摘要中，第二次不得包含完整 `areas` 与 `edges` 数组。
