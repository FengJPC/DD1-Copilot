# 城镇生命与饰品事务

日期：2026-10-06；版本：0.2.4。

## 生命值的来源

城镇名单的底层 actor 有时给出 `1/max`。尚未证明分子代表城镇当前生命，因此 compact、delta 和决策不再把它当作濒死证据，也不擅自改成满血。模型得到 `health: {source: "town_actor", currentHpVerified: false, maxHp}`；无法解析最大值时省略 `maxHp`。地下城的实时生命读数保持原有语义。

城镇观察写入档案时移除旧 `currentHp`/`maxHp`，将它们保存在 `lastRaidHealth`，并写入 `townHealth` 和 `healthSource: "town_unverified"`。进入地下城后，新观察重新建立 `currentHp`。原始日志、full 诊断和历史观察仍保留原读数；不会批量删除旧数据库记录。

人物档案中的建筑训练信息必须由名单入口地址与 focused hero 地址匹配到同一 GUID，不能因为“建筑选中了 A”就将缓存中 B 的职业或训练写给 A。

## 原生饰品动作

```json
{"kind":"equip_trinket","heroGuid":11,"itemId":"当前库存物品ID","slot":0,"inventorySlot":3}
```

```json
{"kind":"unequip_trinket","heroGuid":11,"itemId":"当前装备物品ID","slot":0}
```

`slot` 为 0 或 1。所有 ID 来自新观察；相同物品 ID 对应多个库存格时必须提供 `inventorySlot`。替换装备先卸下再装备，分别核对；不将两个操作伪装成原子事务。

完整库存快照包含物品 ID、实际物理格、数量、名称、效果、职业要求及 `nativeControl`。begin 清理旧库存；只有条数一致的 end 才标记 complete；不可读时清除旧快照。城镇紧凑状态同时提供名单 GUID、当前饰品槽与库存。

Copilot 先检查阶段、快照完整性、能力、英雄可用性、槽状态、物品身份、重复装备和库存歧义。DLL 在游戏主线程重新查询 GUID、物品 ID、数量、两套库存边界和游戏自身的职业资格。

装备调用游戏物品转移函数及属性/名单刷新；卸下调用已有内部卸装回调。均不使用鼠标、模拟按键或复制物品结构。操作后的名单与库存快照包含在本次命令日志内。

## 完成证据

传输 queued 与 command accepted 都不能单独证明装卸完成。成功要求：

1. 本次 command ID 的 begin/end 且 accepted=1；
2. 命令范围内目标 GUID 和槽的饰品观察，以及完整库存快照；
3. 目标槽确实装上指定物品或变空；
4. 同物品 ID 的库存总数恰好减少或增加 1。

异常、连接中断、快照缺失或两侧结果不一致返回 uncertain，不自动重发。请求 ID 去重沿用可持久化的动作回执。

## 当前限制与验证边界

- 原生装卸只开放给已核对函数位置的 Steam 构建；不开放 DRM-free 和斗技场装备操作。
- 当前只转移数量为 1 的饰品格；目标槽必须为空，卸装要求仓库已有可核对的空格。
- 函数位置及转移后的刷新路径已通过本机游戏二进制静态分析；编译和离线工作流测试不证明实机效果。
- 下次测试档应验收两格装卸、职业限制、属性变化、仓库变化以及退出/重进后的持久化。城镇当前生命的可靠来源仍需要进一步实机核对。

DLL 源码与二进制仍遵循现有第三方分发边界，公开插件只包含自有运行时。
